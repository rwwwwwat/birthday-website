## 已确认问题

### F-01：003缺少继承与既有权限的拒绝检查 — P1，迁移/上线前阻断

位置：`database/postgresql/003_grant_runtime_permissions.sql:9`至15的角色检查，以及18至22的GRANT。

该检查核对rolcanlogin、rolsuper、rolbypassrls、直接schema/table owner及几个角色名称，但不检查：

- pg_auth_members的成员关系、可继承权限及SET ROLE路径。
- 已有DELETE、UPDATE(content)、CREATE等有效权限。
- 其他角色属性、继承角色的owner/管理权限是否超出运行时需要。

独立探针使用新的PGlite memory://实例加载原001和原003，未改写脚本：

1. 新建仅供审查的NOLOGIN角色review_power，授予目标表DELETE与UPDATE(content)。
2. 新建LOGIN、NOSUPERUSER、NOBYPASSRLS的review_inherited，允许继承review_power。
3. 让原003处理该角色，脚本成功执行；角色自身不是owner、不是superuser、没有BYPASSRLS。
4. SET ROLE后，对仅存在内存中的合成记录700执行UPDATE(content)及DELETE，均成功，影响各1行。
5. 另一新内存实例中，预先授予review_existing对schema的CREATE权限；003同样成功执行，随后该角色成功创建额外表。

结果证据：`.local/phase10-5-final-role-probe-result.json`中的inheritedPrivileges和preexistingCreate均为confirmedFailure=true。

准确含义：003本身没有新增DELETE或CREATE权限；它没有识别、拒绝或消除这些已存在的有效权限，因此“003执行成功”不能作为最小权限已满足的证明。原脚本末尾及旧报告确实要求额外人工审查，但尚未满足本次明确的完整权限验收条件。这不是已经发生真实数据库越权的证据。

建议在另行授权的修复阶段补齐角色及有效权限前置审查，并增加有继承/已有授权的反例回归；仅设置NOINHERIT不足以替代对SET ROLE路径的审查。本轮不实施修复，不撤销权限，不创建任何真实角色。

### F-02：现有权限测试只覆盖干净角色 — P2，测试覆盖缺口

位置：`backend/BirthdayWebsite.Api.Tests/scripts/postgres-script-check.mjs`末尾权限组。

测试新建无成员关系、无额外授权的角色，再验证新增/已读可用、改正文/删除/建表失败。这些验证是真实SQL而非字符串断言，但未提供F-01条件，因此7组全部通过不能证明任何现有运行角色都满足最小权限。

此外，原权限组在001执行后才创建anon/authenticated，未走001中“已有角色撤权”的分支。本轮独立探针额外先建立这两个角色并预授默认权限，再执行原001，确认schema、table、helper function的相应权限被撤销：该补充验证PASS。

## 1. Provider与原SQL Server

已检查Program.cs、Data目录、Services目录、csproj、相关工厂/业务/配置测试及原SQL Server脚本。

DatabaseProviderSelection在Development默认SqlServer，允许显式PostgreSql；非Development默认PostgreSql，显式SqlServer或未知值直接报错。Program只实例化选中Provider的连接工厂作配置检查，不在启动时打开连接、执行DDL或迁移。

Database:Enabled=true而PostgreSQL必要连接配置缺失时，工厂构造失败，不回退SQL Server。Enabled=false时IWishService为UnavailableWishService，保存抛出DatabaseUnavailableException；PostgreSQL工厂不建立DataSource，OpenAsync拒绝，不会返回伪造的持久化结果。现有Controller和异常处理保留503语义。

原SqlConnectionFactory仍强制Windows认证、加密、受限超时及ConnectRetryCount=0；原SqlWishService仍用参数化INSERT/OUTPUT并在事务提交后返回。原SqlAdminWishService与SqlDatabaseHealthProbe未改动。SQL Server编译/隔离回归通过不等于本轮测试了真实SQL Server连接。

原建库脚本仍声明BirthdayWebsiteDB、五字段、三个默认约束、两个非空白CHECK及两个非聚集索引。原CHECK具体移除TAB/LF/CR后修剪ASCII空格，已与PostgreSQL表达式对照；原脚本未执行。

## 2. Npgsql及业务代码

PostgresConnectionFactory使用Npgsql10.0.3，单例工厂持有DataSource并提供异步Dispose。池0–5、命令/连接/总操作超时有界，Require配置为VerifyFull，禁用自动Prepare、Multiplexing、参数日志和详细数据库错误。构造不打开网络连接，未发现应用级重试循环。

PostgresOperation在await using中释放连接；业务服务异步释放command、reader及transaction。代码检查和替身计数未发现明显连接泄漏；真实网络故障或长期压力下的池行为未测，不能据此承诺实测无泄漏。

内容、source、id、分页offset/size均以DbParameter传递。动态筛选仅由bool?选择固定WHERE，不拼接用户文本。INSERT只写content及服务器固定source，RETURNING取得id/时间/余数/已读/来源，reader结束后CommitAsync成功才返回；失败时没有重试。WishesController在服务返回后才生成201。

分页count与rows在同一RepeatableRead事务，统计与latest同样使用一个快照；详情和标记已读保留原返回结构、缺失记录语义及提交后返回。健康查询只有SELECT 1。实际多连接并发隔离、网络断开后提交状态仍属后续集成验证。

Cloudflare Access、管理员Cookie/Authorize、CSRF及限流中间件没有因本阶段改造被移除或重排到静态文件之后；原相应回归测试均在本轮232项中重新运行。

## 3. CreatedAt

现有SQL Server服务明确将DATETIME2读出的DateTime标记为UTC，再转换DateTimeOffset。新PreciseUtcTimestamp对DateTimeOffset先取UTC，余数为Ticks%10，微秒为Ticks-余数；Join要求UTC、微秒对齐及0–9余数，再精确加回。FromSqlServerUtc仅用于已确认UTC语义的SQL字段，拒绝Local类型。

时间单元测试包含全部十种余数、1万组随机Ticks、最小/最大值、2000年之前日期、非零offset和非法输入。本轮均通过。

PGlite实际将`.1772829`、`.1772821`存储为同一微秒及不同余数，再使用to_char加余数读取七位时间；同时实际测试0001年最小值与9999年最大值。因此精度结论不是仅由C#测试得出。

数据库默认clock_timestamp()写入timestamptz，表示一个时刻，不依赖把服务器当地时间当UTC；Npgsql按UTC读取的代码契约正确。普通新建记录余数默认0，迁入记录使用原余数。表拒绝infinity及超出.NET范围的值；工厂关闭Npgsql的Infinity特殊映射。

分页、latest及两条索引均包含created_at、remainder、wish_id的完整降序。同微秒内余数不同的排序已在真实内存引擎验证，不能删除余数后仍声称保持100ns排序。Npgsql真实线协议与Supabase往返时间仍BLOCKED，未进行网络连接。

- 首次安装脚本遇已存在schema明确失败，不覆盖；不是静默幂等脚本。

### 002 — PASS（受控导入前提下）

- BEGIN、固定schema、事务锁及表锁；必须提供已审查的同连接JSON与源identity设置。
- 目标非空立即拒绝，没有UPDATE/DELETE或覆盖分支。

- 实际验证重复ID、错误类型/长度/日期、重复导入等失败，显式ROLLBACK后确认合成记录未部分保留。
- 测试中的ROLLBACK由测试调用者发出；脚本失败后事务处于失败状态，不能声称任意客户端会自动结束连接或释放事务。未来应按文档使用新连接、ON_ERROR_STOP并正确结束失败事务。
- setval取最大记录ID、源identity及现有序列位置的最大值，正常导入案例下一编号为151而不是重用101/102。
- setval不受事务回滚保护，文档已提示可能留空隙。现有测试没有制造提交时网络中断，不能把它当作真实提交故障验收。迁移完成前必须禁写并只读核对序列。

干净角色被授予SELECT/INSERT/UPDATE(is_read)、schema/函数使用和序列USAGE，且默认没有DELETE、正文修改、CREATE权限，这部分PASS。但F-01反例证明既有/继承权限未检查，不能完成本次“无额外高权限”的验收。
